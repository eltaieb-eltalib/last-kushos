# خطة بناء منصة الوكيل الذكي السحابي (Cloud-based Autonomous Personal Computer Agent Platform)

> **الفكرة باختصار:** كل مستخدم يحصل على "كمبيوتر شخصي" كامل يعمل في السحابة داخل آلة افتراضية **QEMU/KVM**،
> ووكيل ذكاء اصطناعي (Agent) **يرى الشاشة ويتحكم في الفأرة ولوحة المفاتيح** وينفّذ المهام نيابةً عن المستخدم
> بشكل ذاتي (تثبيت برامج، ملء نماذج، تشغيل ملفات، تصفح، ...)، والمستخدم يتابع ويتدخل مباشرة من المتصفح.
>
> **نظام التشغيل الأول المستهدف:** Kush OS (هذا المستودع، المبني على ReactOS) — ثم Linux وWindows لاحقاً.

---

## 1. الأهداف

| الهدف | الوصف |
|---|---|
| حاسوب لكل مستخدم | آلة QEMU معزولة لكل مستخدم/جلسة، تُنشأ في ثوانٍ من صورة جاهزة (Golden Image). |
| وكيل ذاتي | حلقة: لقطة شاشة ← تفكير (LLM) ← فعل (نقر/كتابة/أمر) ← تحقّق، حتى إنجاز المهمة. |
| تحكم بشري دائم | بث مباشر للشاشة (noVNC/WebRTC)، زر "إيقاف/استلام التحكم" في أي لحظة. |
| أمان وعزل | لا يخرج الوكيل من الآلة الافتراضية، صلاحيات شبكة محددة، تأكيد بشري للأفعال الحساسة. |
| قابلية التوسع | آلاف الآلات المتزامنة على عناقيد خوادم bare-metal تدعم KVM. |
| استمرارية | لقطات (Snapshots) لحالة الجهاز، استرجاع فوري عند خطأ الوكيل. |

## 2. خارج النطاق (في الإصدار الأول)
- تطبيق موبايل أصلي (الواجهة ويب متجاوبة فقط).
- دعم GPU داخل الآلات الافتراضية.
- سوق إضافات (Marketplace).

## 3. البنية العامة (Architecture)

```
 ┌──────────────┐      HTTPS/WebSocket      ┌─────────────────────────────┐
 │  واجهة الويب  │ ───────────────────────▶ │   API Gateway + Auth         │
 │ (Next.js +   │ ◀── بث الشاشة (WebRTC) ── │   (Control Plane)            │
 │  noVNC)      │                           └──────────┬──────────────────┘
 └──────────────┘                                      │
                       ┌───────────────────────────────┼──────────────────────────┐
                       ▼                               ▼                          ▼
              ┌────────────────┐            ┌───────────────────┐       ┌──────────────────┐
              │ Task / Session │            │  Agent Runtime     │       │  VM Orchestrator │
              │   Service      │◀──────────▶│ (حلقة الوكيل+LLM)  │◀─────▶│  (جدولة الآلات)  │
              │ (Postgres)     │            └─────────┬─────────┘       └────────┬─────────┘
              └────────────────┘                      │ أوامر أدوات              │ gRPC
                                                      ▼                          ▼
                                       ┌──────────────────────────────────────────────────┐
                                       │           Host Node (خادم bare-metal + KVM)       │
                                       │  ┌───────────── Node Agent (Go/Rust) ───────────┐ │
                                       │  │  QMP  │  VNC  │  virtio-serial │ Snapshots   │ │
                                       │  └───┬───────┬──────────┬─────────────┬────────┘ │
                                       │      ▼       ▼          ▼             ▼          │
                                       │   ┌──────────────────────────────────────┐       │
                                       │   │  QEMU VM  (Kush OS / Linux / Win)    │       │
                                       │   │   └─ Guest Agent داخل النظام          │       │
                                       │   └──────────────────────────────────────┘       │
                                       └──────────────────────────────────────────────────┘
```

### 3.1 المكونات الرئيسية

1. **Control Plane (طبقة التحكم):** API، المصادقة، الحسابات، الحصص (Quotas)، الفوترة.
2. **VM Orchestrator (منسّق الآلات):** يختار الخادم المناسب، يُنشئ/يوقف/يأخذ لقطات للآلات، يحتفظ بـ "مسبح دافئ" (Warm Pool) من الآلات الجاهزة.
3. **Node Agent (وكيل الخادم):** خدمة على كل خادم فيزيائي تدير عمليات QEMU محلياً وتعرض واجهة gRPC.
4. **Agent Runtime (محرك الوكيل):** حلقة التفكير والتنفيذ، يتصل بنموذج اللغة ويحوّل قراراته إلى أفعال على الآلة.
5. **Guest Agent (وكيل داخل النظام الضيف):** برنامج صغير داخل Kush OS لتنفيذ أوامر بدقة (تشغيل عملية، قراءة ملف، شجرة النوافذ).
6. **Streaming Gateway (بوابة البث):** تحويل VNC إلى WebSocket/WebRTC لعرض الشاشة في المتصفح.
7. **Storage (التخزين):** صور الأقراص qcow2، اللقطات، ملفات المستخدم، سجلات الجلسات (فيديو + خطوات).

## 4. طبقة التحكم في QEMU (القلب التقني)

### 4.1 تشغيل الآلة
```bash
qemu-system-x86_64 \
  -enable-kvm -cpu host -smp 2 -m 4096 \
  -machine q35 \
  -drive file=user-123.qcow2,if=virtio,cache=writeback \   # طبقة فوق الصورة الذهبية (backing file)
  -netdev user,id=n0,restrict=off -device virtio-net,netdev=n0 \
  -vnc unix:/run/vm/123/vnc.sock \
  -qmp unix:/run/vm/123/qmp.sock,server,nowait \
  -chardev socket,id=ga,path=/run/vm/123/ga.sock,server=on,wait=off \
  -device virtio-serial -device virtserialport,chardev=ga,name=org.kush.agent.0 \
  -device usb-tablet \          # إحداثيات مطلقة للفأرة (مهم جداً لدقة النقر)
  -display none -daemonize
```
> ملاحظة لـ Kush/ReactOS: نبدأ بـ `e1000` و`ide`/`ahci` إن لم تكن تعريفات virtio مستقرة، ثم ننتقل إلى virtio بعد الاختبار.

### 4.2 قنوات التحكم الثلاث

| القناة | الاستخدام | الملاحظات |
|---|---|---|
| **QMP** (QEMU Machine Protocol) | `screendump` لأخذ لقطة شاشة، `input-send-event` للفأرة/لوحة المفاتيح، `savevm/loadvm`، `stop/cont`، `query-status` | لا يحتاج أي شيء داخل النظام الضيف — يعمل حتى أثناء الإقلاع والشاشة الزرقاء. **القناة الأساسية.** |
| **VNC** | بث الشاشة للمستخدم، وبديل للإدخال | يُمرَّر عبر noVNC/WebRTC للمتصفح. |
| **virtio-serial + Guest Agent** | تنفيذ أوامر، نقل ملفات، قراءة شجرة واجهة المستخدم (UI Automation)، الحافظة | أسرع وأدق من الرؤية، لكن يحتاج برنامجاً داخل النظام. |

### 4.3 أدوات الوكيل (Tool API) — طبقة تجريد موحّدة
```
screenshot()                         → صورة PNG (مصغّرة إلى 1280x800 مثلاً)
click(x, y, button="left", double=False)
move(x, y) / drag(x1,y1,x2,y2)
type_text("...")                     → تحويل النص إلى سلسلة qcode مع دعم العربية عبر Guest Agent/الحافظة
key("ctrl+alt+delete") / key("win+r")
scroll(x, y, dx, dy)
wait(seconds) / wait_for_screen_change()
run(command)                         → عبر Guest Agent
read_file(path) / write_file(path)   → عبر Guest Agent
ui_tree()                            → شجرة النوافذ والأزرار (عبر Guest Agent)
snapshot(name) / restore(name)       → عبر QMP
```
- **تحويل الإحداثيات:** الصورة المرسلة للنموذج مصغّرة؛ يجب تحويل الإحداثيات للأبعاد الحقيقية ثم إلى مدى usb-tablet المطلق (0–32767).
- **الكتابة بالعربية:** `input-send-event` يرسل مفاتيح فيزيائية لا حروفاً؛ لذلك النص العربي/Unicode يُرسل عبر Guest Agent (`SendInput` مع `KEYEVENTF_UNICODE`) أو عبر الحافظة + Ctrl+V.

### 4.4 Guest Agent لـ Kush OS
- برنامج Win32 صغير (C) يُبنى ضمن شجرة المستودع (مثلاً `modules/kushagent/`) ويُضاف للصورة الذهبية ويعمل كخدمة.
- يتصل بمنفذ virtio-serial (أو COM1 كبديل إن لم يتوفر تعريف virtio-serial على ReactOS).
- بروتوكول: JSON-RPC سطري (`{"id":1,"method":"run","params":{...}}`).
- الوظائف: `run`, `read_file`, `write_file`, `list_windows`, `ui_tree` (عبر EnumWindows/Accessibility)، `clipboard_set/get`, `type_unicode`, `ping`.
- **ملاحظة:** qemu-guest-agent الرسمي لويندوز قد لا يعمل على ReactOS، لذا نكتب وكيلاً خاصاً بسيطاً.

## 5. محرك الوكيل (Agent Runtime)

### 5.1 الحلقة الأساسية
```
1. استلام المهمة من المستخدم (مثال: "ثبّت Firefox وافتح موقع الجامعة").
2. التخطيط: تقسيم المهمة لخطوات فرعية (Planner).
3. لكل خطوة:
   a. screenshot (+ ui_tree إن توفر)
   b. إرسال الصورة + السياق + الأدوات إلى نموذج اللغة (مع دعم Computer Use)
   c. استلام فعل → التحقق من سياسة الأمان → التنفيذ عبر Node Agent
   d. انتظار استقرار الشاشة → لقطة جديدة → تقييم النجاح
4. عند الفشل المتكرر: restore لآخر snapshot وإعادة المحاولة بخطة مختلفة، أو طلب مساعدة المستخدم.
5. تقرير نهائي + تسجيل فيديو للجلسة.
```

### 5.2 قرارات التصميم
- **النموذج:** نموذج يدعم "Computer Use" (مثل نماذج Claude الحديثة) مع إمكانية تبديل المزوّد عبر طبقة تجريد.
- **إدارة السياق:** الاحتفاظ بآخر N لقطات فقط + ملخص نصي للخطوات السابقة لتقليل التكلفة.
- **ذاكرة طويلة المدى:** تفضيلات المستخدم، كلمات مرور مخزّنة في خزنة (Vault) لا يراها النموذج مباشرة بل تُحقن عند الطلب.
- **Human-in-the-loop:** أفعال تحتاج موافقة (دفع، حذف ملفات، إرسال بريد، إدخال كلمة مرور).
- **المهام المجدولة:** تشغيل مهام دورية (كل صباح: افتح البريد ولخّصه).
- **تعدد الوكلاء:** لاحقاً — وكيل منسّق يوزع المهام على عدة آلات بالتوازي.

### 5.3 نماذج خارجية قابلة للتبديل حسب الـ Prompt (Bring Your Own Model)

**الفكرة:** النظام الضيف (Kush) لا يحتوي أي ذكاء اصطناعي. كل النماذج **خارجية** وتتحكم فيه **من الخارج** عبر طبقة الأدوات (QMP + VNC + Guest Agent). المستخدم يختار النموذج، أو يكتب في الـ prompt ما يريد، والموجّه (Router) يختار النموذج المناسب.

```
 Prompt المستخدم ──▶ Model Router ──▶ [Claude | GPT | Gemini | Qwen-VL محلي | نموذج المستخدم الخاص]
                                            │  (كلها تتكلم نفس Tool API)
                                            ▼
                                  Agent Runtime ──▶ Node Agent ──▶ QMP/VNC/Guest Agent ──▶ Kush في QEMU
```

**المكونات:**
1. **Model Adapter (محوّل موحّد):** واجهة واحدة لكل المزوّدين:
   ```python
   class ModelAdapter:
       def step(self, task, history, screenshot, tools) -> Action: ...
   ```
   لكل مزوّد محوّل يترجم Tool API (قسم 4.3) إلى صيغة أدوات المزوّد:
   - Anthropic (أداة Computer Use الأصلية)
   - OpenAI / Azure (Function Calling أو Computer Use)
   - Google Gemini
   - نماذج محلية/خاصة: Ollama، vLLM، أو أي Endpoint متوافق مع OpenAI (مثل Qwen-VL، UI-TARS)
   - **نموذج المستخدم الخاص:** يدخل المستخدم `base_url` + `api_key` (يُحفظ مشفّراً في الخزنة).

2. **Model Router (موجّه حسب الـ prompt):**
   - **اختيار صريح:** `@claude ثبّت Firefox` أو `@local افتح Notepad` أو اختيار من قائمة في الواجهة.
   - **قواعد يكتبها المستخدم (YAML):**
     ```yaml
     routes:
       - match: "تثبيت|install"      ; model: claude      # مهام معقدة متعددة الخطوات
       - match: "اكتب|type|notepad"  ; model: local-qwen  # مهام بسيطة ورخيصة
       - default: gpt
     fallback: [claude, gpt]        # إذا فشل نموذج يُجرّب التالي
     ```
   - **توجيه ذكي (اختياري):** نموذج صغير يصنّف المهمة (بسيطة/معقدة/حساسة) ويختار الأرخص القادر.
   - **وضع مختلط:** نموذج قوي "مخطِّط" (Planner) + نموذج سريع "منفِّذ" (Executor) لكل نقرة.

3. **التحكم الخارجي المباشر (لمن عنده وكيل جاهز):**
   - **API عامة (REST + WebSocket):** `POST /vms/{id}/actions` (`screenshot`, `click`, `type`, ...) ليتحكم أي برنامج أو نموذج خارجي في الجهاز بنفسه.
   - **MCP Server:** نعرض أدوات الجهاز كخادم MCP، فيستطيع أي عميل يدعم MCP (Claude Desktop، Claude Code، أو وكلاء أخرى) أن يتحكم في Kush مباشرة.
   - **SDK** صغير (Python/JS): `vm = kush.connect(id); vm.click(100,200)`.
   - توكنات وصول لكل جهاز بصلاحيات محددة (قراءة الشاشة فقط / تحكم كامل) ومدة صلاحية.

4. **ضوابط مشتركة لكل النماذج:** نفس Policy Engine والموافقات البشرية وسجل التدقيق تُطبَّق مهما كان النموذج، لأن كل الأفعال تمر عبر Tool API نفسها. حدود تكلفة وخطوات لكل نموذج، ومقارنة أداء النماذج على مجموعة التقييم (Eval Suite) لاختيار التوجيه الأفضل.

## 6. التخزين وإدارة الصور

- **Golden Image:** صورة qcow2 لـ Kush OS مثبّت مسبقاً + Guest Agent + برامج أساسية، تُبنى آلياً من `bootcd.iso` عبر CI (يوجد بالفعل `release.yml`).
- **Copy-on-Write:** كل مستخدم يحصل على ملف qcow2 رفيع مبني على الصورة الذهبية (`qemu-img create -b golden.qcow2 -F qcow2 user.qcow2`) ← إنشاء في أقل من ثانية.
- **اللقطات:** `savevm` (ذاكرة + قرص) للاسترجاع السريع داخل الجلسة، ونسخ القرص إلى Object Storage (S3/MinIO) عند إيقاف الآلة.
- **الإقلاع السريع:** استعادة الآلة من لقطة ذاكرة جاهزة (النظام مُقلع مسبقاً) بدلاً من الإقلاع الكامل ← ثوانٍ قليلة.
- **ملفات المستخدم:** قرص ثانٍ دائم أو مجلد مشترك (virtio-9p/virtiofs إن دُعم، وإلا رفع/تنزيل عبر Guest Agent).

## 7. البنية التحتية السحابية

| الطبقة | الاختيار المقترح |
|---|---|
| الخوادم | bare-metal يدعم KVM (Hetzner، OVH، AWS `.metal`، أو GCP مع Nested Virtualization). |
| تنسيق الحاويات للخدمات | Kubernetes (للـ Control Plane والـ Agent Runtime). |
| الآلات الافتراضية | Node Agent مخصص يدير QEMU مباشرة (أو KubeVirt كبديل). |
| قاعدة البيانات | PostgreSQL + Redis (طوابير وحالة الجلسات). |
| الطوابير | NATS أو Redis Streams. |
| التخزين | S3 / MinIO للصور والتسجيلات. |
| البث | noVNC + websockify أولاً، ثم WebRTC (لزمن استجابة أقل). |
| المراقبة | Prometheus + Grafana + Loki + OpenTelemetry. |
| السرّية | HashiCorp Vault / KMS. |

**تقدير السعة:** خادم بـ 64 نواة و256GB RAM ≈ 40–60 آلة Kush (2 vCPU، 2–4GB) مع overcommit معقول؛ Kush أخف بكثير من Windows.

## 8. الأمان والعزل

1. **عزل الآلة:** QEMU يعمل كمستخدم غير root، داخل cgroups + seccomp (`-sandbox on`) + AppArmor/SELinux (sVirt).
2. **الشبكة:** كل آلة في شبكة معزولة؛ جدار ناري يمنع الوصول لشبكة السحابة الداخلية (metadata endpoints)، وقوائم سماح للنطاقات حسب خطة المستخدم.
3. **أمان الوكيل:**
   - حماية من Prompt Injection عبر محتوى الشاشة (النص الظاهر في المواقع لا يُعامل كأوامر).
   - سياسة أفعال (Policy Engine): قائمة أفعال ممنوعة/تحتاج موافقة.
   - حدود: عدد خطوات أقصى، زمن أقصى، تكلفة قصوى لكل مهمة.
4. **البيانات:** تشفير الأقراص (LUKS على المضيف أو تشفير qcow2)، تشفير أثناء النقل (TLS)، حذف آمن عند إنهاء الحساب.
5. **سجل تدقيق (Audit Log):** كل فعل للوكيل مسجّل مع لقطة الشاشة قبله وبعده.
6. **إساءة الاستخدام:** منع التعدين، الإرسال الجماعي للبريد، الهجمات؛ مراقبة استهلاك الموارد والشبكة.

## 9. واجهة المستخدم (Web App)

- **لوحة التحكم:** قائمة الأجهزة، حالتها، زر تشغيل/إيقاف/لقطة.
- **شاشة الجلسة:**
  - يسار: الشاشة الحية (noVNC) مع زر "استلم التحكم".
  - يمين: محادثة مع الوكيل + خطواته الحالية + أزرار الموافقة.
  - أسفل: شريط زمني (Timeline) لكل الخطوات مع لقطاتها، وإمكانية "الرجوع لهذه النقطة".
- **المهام المجدولة والقوالب.**
- **دعم كامل للعربية و RTL** في الواجهة.

### المرحلة 0 — إثبات المفهوم (2–3 أسابيع)
- [ ] سكربت Python يشغّل Kush OS في QEMU محلياً مع QMP.
- [ ] دوال: `screenshot` (screendump) و`click`/`type` (input-send-event) مع usb-tablet.
- [ ] ربط حلقة وكيل بسيطة بنموذج لغة: مهمة "افتح Notepad واكتب Hello".
- [ ] قياس: دقة النقر، زمن كل خطوة، تكلفة المهمة.
- **معيار النجاح:** الوكيل ينجز 5 مهام بسيطة على Kush بدون تدخل.

### المرحلة 1 — Guest Agent وصورة ذهبية (3–4 أسابيع)
- [ ] كتابة `kushagent.exe` (C/Win32) والتواصل عبر virtio-serial أو COM1.
- [ ] الكتابة بـ Unicode/العربية، تشغيل الأوامر، نقل الملفات، قائمة النوافذ.
- [ ] Pipeline في GitHub Actions: من `bootcd.iso` إلى صورة qcow2 ذهبية مثبتة آلياً (تثبيت غير تفاعلي `unattend`).

### المرحلة 2 — Node Agent والمنسّق (4–6 أسابيع)
- [ ] Node Agent (Go أو Rust) بواجهة gRPC: create / start / stop / snapshot / restore / screenshot / input / exec.
- [ ] Orchestrator: جدولة على عدة خوادم، Warm Pool، إيقاف الآلات الخاملة تلقائياً.
- [ ] تخزين الصور على S3 ومزامنتها للخوادم.

## 12. المخاطر وطرق التخفيف

| الخطر | التخفيف |
|---|---|
| عدم استقرار تعريفات virtio على Kush/ReactOS | البدء بـ e1000/AHCI/COM1، وتحسين virtio تدريجياً داخل هذا المستودع. |
| دقة النقر ضعيفة من الرؤية فقط | usb-tablet بإحداثيات مطلقة + ui_tree من Guest Agent + دقة شاشة ثابتة (مثلاً 1024x768). |
| تكلفة نماذج اللغة عالية | تصغير الصور، تقليل اللقطات، كشف "الشاشة لم تتغير"، نماذج أصغر للخطوات البسيطة. |
| بطء الإقلاع | لقطات ذاكرة جاهزة + Warm Pool. |
| Prompt Injection وأفعال ضارة | Policy Engine + موافقات بشرية + عزل الشبكة + سجل تدقيق. |
| تكلفة الخوادم | Kush خفيف، overcommit للذاكرة (KSM)، إيقاف الآلات الخاملة. |
| توافق البرامج مع Kush | قائمة برامج مختبرة (Firefox وغيرها كما في `docs/`)، وتوفير Linux/Windows كبديل. |

## 13. مؤشرات النجاح (KPIs)
- نسبة إنجاز المهام بدون تدخل بشري ≥ 70% على مجموعة التقييم.
- زمن بدء الجهاز ≤ 5 ثوانٍ (من Warm Pool).
- زمن الخطوة الواحدة للوكيل ≤ 3–5 ثوانٍ.
- تكلفة الساعة لكل جهاز + وكيل ضمن هامش ربح مستهدف.
- صفر حوادث هروب من الآلة الافتراضية.
